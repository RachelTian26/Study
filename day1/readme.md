# 日历工作台 — 项目总结与向导

## 项目概述

一个带 AI 智能解析的日历工作台，支持**月/周/日**三种视图，可以在时间网格上直观地创建、编辑、完成和推迟工作事项。后端通过密码认证保护数据，支持浏览器通知提醒，AI 助手用自然语言即可自动填充事项表单。

**新增功能（2026-07-16）**：浏览器通知提醒系统、推迟/延长操作、搜索筛选、循环重复事项、个人信息库。

**技术栈**：React 19 + Vite（前端） / Express 5 + SQLite（后端） / 火山引擎方舟 API（AI）

## 核心主题：如何引导 AI 一步步达成项目目标

这是本项目最重要的经验。整个日历工作台不是"一次说清楚需求然后 AI 一把梭"做出来的，而是通过**持续反馈、逐步纠偏、具体化指令**，让 AI 沿着正确的方向迭代。以下是真实对话中每一轮引导的复盘。

### 第一阶段：把模糊想法变成具体方案

**我说的**：我要创建一个网站，能够跟日历一样，可以在日历上显示和记录更改我的工作项。还能发通知和提醒。

**AI 怎么反应**：开始讨论设计方案。

**引导技巧**：这个阶段我没有让 AI 直接写代码，而是先"讨论设计"。因为需求还很模糊——功能边界、交互方式、技术选型都没定，直接写代码等于让 AI 瞎猜。**先对齐认知，再动手。**

### 第二阶段：用具体约束缩小范围

**我说的**：周视图，全天，固定几个 10分钟 30分钟 1个小时，1天，2天。

**AI 怎么反应**：根据这些约束开始搭建具体的视图和时长选项。

**引导技巧**：我没有说"做一个好看的日历"，而是给了精确的时长选项列表。**AI 不怕信息多，怕信息模糊。** 给具体数字、枚举值，比给形容词效果好一百倍。

### 第三阶段：部署和安全的现实约束

**我说的**：这个应用如何让我在多个不同的电脑上使用 → 我只有一台云服务器 → 最好有一个密码，不能随便让人用 → 密码作为 .env，给 .env.sample，gitignore .env

**AI 怎么反应**：实现了 JWT 登录认证、bcrypt 密码哈希、环境变量配置。

**引导技巧**：这里的关键是**逐步追加约束**。先说"多端使用"，AI 可能建议云服务；我说"只有一台云服务器"，AI 就聚焦到单服务器部署；再说"要密码"，AI 就加上认证。**一次只给一个约束，让 AI 在上一轮理解的基础上迭代，而不是一口气扔十个需求。**

### 第四阶段：发现缺陷，精准描述

**我说的**：点击"新建事项"后：第一，没有 AI 模型帮你主动输入待办事项，需要添加 AI 模型；第二，日历缺少具体时间段，在填写新建事项时应该包括"标题""开始时间""预计需要时长""详细内容"。

**AI 怎么反应**：添加了 AI 解析功能和完整的表单字段。

**引导技巧**：我没有说"功能不好用"，而是**精确指出了两个缺失**：AI 能力缺失、表单字段缺失。这种"列举式"的反馈让 AI 可以逐条处理，不会遗漏。

### 第五阶段：配置具体化——不给 AI 猜的空间

**我说的**：模型配置用火山引擎方舟的 codingplan，URL 是 xxx，秘钥是 xxx，模型使用 deepseek-v4-pro，配置到 .env 里面。

**AI 怎么反应**：直接配置，不需要自己找 API 地址或猜模型名。

**引导技巧**：第三方 API 配置如果让 AI 自己查文档，很容易出错。**把 URL、Key、Model 一次性给全**，AI 只需要做集成工作。

### 第六阶段：AI 解析失败——坚持反馈，不放弃

**我说的**：AI 解析不对，明天下午没有更新日期；默认值最好给输入；输入框比较小；建议给导入数据功能。

**AI 怎么反应**：但 AI 第一轮只修了部分，AI 解析仍然失败。

**我说的**：延期这个项目到周五吧，说 AI 解析失败。

**另一个 AI 诊断**：发现 `deepseek-v4-pro` 是推理模型，`max_tokens: 300` 不够——token 全被内部思考吃掉了，实际输出为空。

**引导技巧**：这是整项目最关键的一课。AI 解析失败时，我没有放弃这个功能，而是**持续反馈"还是不行"**。最终诊断出根本原因是推理模型的 token 配置问题，而不是 Prompt 写错了。**当 AI 做的结果不对时，不要接受"勉强能用"，追到底。**

### 第七阶段：口语时间不识别——分层解决

**我说的**：输入"2点半"不会自己改，表单输入项要更智能，最大 tokens 可以到 10k。

**AI 怎么反应**：1）max_tokens 提到 10000；2）优化 AI Prompt 增加中文时间映射规则；3）前端加 `parseSmartTime()` 函数做本地解析兜底。

**引导技巧**：这里体现了**双层防御**的思路——既让 AI 模型更聪明（Prompt 优化），又让前端在 AI 不可用时照样工作（本地解析）。**永远不要只依赖 AI 一条路径。**

### 第八阶段：视觉问题——用对比描述

**我说的**：时间比如 9 点 11 点每天应该对齐，而不应该很乱看起来堆砌。

**AI 怎么反应**：把周视图和日视图从简单卡片堆叠重构为时间轴网格布局，事件按 startTime 绝对定位。

**引导技巧**：我没有说"布局不好看"，而是**用对比描述**——"应该对齐"vs"很乱看起来堆砌"。这让 AI 立刻理解了问题本质：不是美化，而是**时间轴对齐**这个功能性需求。

### 第九阶段：提醒系统——先讨论再动手

**我说的**：软件缺少提醒功能。一个任务的开始和结尾都应该有提醒弹窗。先不要写代码，我们沟通好具体细节再开始。

**AI 怎么反应**：先列出方案 A/B/C 让我选择。

**引导技巧**：复杂功能在写代码之前先对齐方案。我选了"浏览器系统通知+应用内弹窗"，明确了推迟/延长/完成/未完成四种操作，以及日历上虚线标注的视觉方案。**讨论花费 5 分钟，但省去了写完重做的 2 小时。**

### 第十阶段：服务挂了——坚持修到能跑

**我说的**：服务器坏了，修不好就把数据库重建。→ 后来又说：无法访问此网站，ERR_CONNECTION_REFUSED。

**AI 怎么反应**：多次尝试修复，最终发现是 Express 5 默认只监听 IPv6 导致 `localhost` 无法访问，改成 `0.0.0.0` 绑定解决。

**引导技巧**：部署问题很容易让人沮丧。**不要因为"服务器连不上"就放弃项目**——这种问题往往是某个配置细节，不是架构问题。坚持让 AI 排查，最终定位到一行代码。

## 引导 AI 的核心原则总结

| 原则 | 错误做法 | 正确做法 |
|------|----------|----------|
| **具体化** | "把界面做好看点" | "9 点和 11 点的事件应该对齐到时间网格" |
| **逐步追加** | 一口气扔 10 个需求 | 先做基础日历 → 再加认证 → 再加 AI → 再优化布局 |
| **列举反馈** | "功能不好用" | "第一，AI 不能解析；第二，表单缺少时间字段；第三，输入框太小" |
| **配置给全** | "接入一个 AI 模型" | "API 地址 xxx，Key xxx，模型名 deepseek-v4-pro" |
| **追到底** | AI 解析失败就放弃 | 持续反馈"还是不行"→ 定位到 max_tokens 问题 → 修复 |
| **双层防御** | 只靠 AI 解析 | AI Prompt 优化 + 前端本地解析兜底 |
| **对比描述** | "布局太乱" | "应该对齐到时间线，而不是堆砌在一起" |
| **先讨论后写** | 提醒功能直接写代码 | 先列方案 A/B/C 选型，对齐后再动手 |
| **不放弃部署** | 服务连不上就放弃 | 排查 IPv6 绑定、端口占用等配置细节 |

## 功能全景

### 日历视图
- **月视图**：快速浏览当月所有事项，点击日期查看详情
- **周视图**：时间网格（01:00-24:00），每小时 64px，事件按时间绝对定位，重叠事件自动分列
- **日视图**：同周视图但只显示单日，适合当天详细规划

### 事项管理
- 新建/编辑/删除事项，支持标题、开始时间、预计时长、详细内容
- 往返时间（bufferBefore / bufferAfter），例如上课前 5 分钟准备 + 路程时间
- AI 智能解析：输入自然语言（"明天下午开会2小时"）自动填充表单
- 前端智能时间解析：输入"2点半"→`14:30`，"下午3点"→`15:00`

### 提醒通知系统（新增）
- **开始前提醒**：可设置多个提醒（开始时、5/15/30分钟前、1/2小时前、1天前、结束时）
- **结束时提醒**：自动弹窗询问任务状态
- 浏览器系统通知 + 应用内弹窗双重提醒
- 操作选项：
  - 开始前：[知道了] [推迟 5 分钟] [推迟 30 分钟]
  - 结束时：[继续 15/30 分钟/1 小时] [✓完成] [✗未完成]
- 推迟的任务在日历上显示原计划虚线框 + 新时间实线框
- 延长的任务在日历上显示 `+X分钟` 标记
- 继续工作结束后再次提醒

### 循环重复事项（新增）
- 支持每天、每周、每两周、每月等重复规则
- 日历自动展开重复事项到对应日期
- AI 解析时能识别"每周三下午例会"等重复表达

### 搜索筛选（新增）
- 顶部搜索框：按标题关键词搜索事项
- 状态筛选：待完成 / 已完成 / 未完成
- 活动类型筛选：按个人信息库中配置的类型过滤

### 个人信息库（新增）
- 年龄、学校/工作单位、固定日程、习惯偏好、活动类型偏好
- 活动类型可自定义（如：学习、健身、滑冰）+ 偏好时间段多选
- AI 根据个人资料智能推荐日程安排（例如"本周加一个健身一小时"）

### 认证与安全
- 密码登录（bcrypt 哈希 + JWT Token）
- `.env` 配置敏感信息，`.env.sample` 提供模板，`.gitignore` 防止泄露

复制 `.env.sample` 为 `.env`：

```env
PORT=3001
APP_PASSWORD=admin123
JWT_SECRET=你的随机密钥
AI_API_KEY=你的火山引擎API Key
AI_API_BASE=https://ark.cn-beijing.volces.com/api/coding/v3

```

### 5. 启动

```bash
# 开发模式
node server/index.cjs &
npx vite --port 5173

# 生产模式
npm run build
node server/index.cjs
# 访问 http://localhost:3001
```

### 6. 后台持久运行（screen 方式）

```bash
screen -dmS calendar bash -c 'cd /path/to/calendar-app && node server/index.cjs'
# 查看：screen -r calendar
# 分离：Ctrl+A, D
```

## 二、核心算法

**时间网格定位**

```
时间轴：01:00 - 24:00（23 小时），每小时 64px
事件 top  = (startMin - 60) / 60 * 64
事件 height = max(duration / 60 * 64, 22px)
```

**重叠事件分列（Lane 算法）**

遍历按时序排列的事件，为每个事件找第一个空闲 lane（前一个已结束）。没有空闲则新建 lane。事件宽度 = `100% / totalLanes`。

**循环事件展开**

遍历日期范围内的每一天，检查每个循环事件的 recurrence 规则是否匹配该日期，匹配则生成虚拟事件实例。

**提醒轮询**

前端每 30 秒轮询 `GET /api/reminders/due`，获取所有未触发的到期提醒。提醒按时间排序，一次显示一个，触发后标记为已触发。

## 三、踩过的坑

| 坑 | 原因 | 解决 |
|----|------|------|
| AI 解析失败 | `max_tokens: 300` 被推理模型的思考过程耗尽 | 提到 10000 |
| 口语时间不识别 | Prompt 没有明确中文时间映射 | Prompt 加规则 + 前端本地解析兜底 |
| 后台进程挂掉 | `nohup &` 在命令间不持久 | 改用 `screen` 会话 |
| 服务器连不上 | Express 5 默认只监听 IPv6 | `app.listen(PORT, "0.0.0.0")` |
| localhost 拒绝连接 | 同一 IPv6 问题 | 同上述修复 |

## 五、学到了什么

**技术层面**：推理模型的 token 限制是隐藏陷阱；Prompt 工程决定 AI 集成成败；前端兜底让系统在 AI 挂掉时仍可用；时间网格定位是日历类应用的核心难点；浏览器 Notification API 需要用户主动授权；Express 5 的 IPv6 默认行为是个坑。

**工程层面**：`.env.sample` + `.gitignore` 是安全底线；`nohup &` 不可靠，screen 更稳定；先跑通再优化，不要一开始就追求完美布局；演示数据让新用户体验好十倍；复杂功能先讨论方案再写代码。

**产品层面**：日历的核心是时间可视化，不是事项列表；AI 是辅助不是替代，表单永远可编辑；提醒系统需要仔细设计状态机（推迟→再次提醒→完成/放弃）；个人信息库是 AI 推荐的基础，数据质量决定推荐质量。

**协作层面**：引导 AI 的关键不是"说得多"，而是**说得准**——具体化、逐步追加、列举反馈、配置给全、追到底、双层防御、对比描述、先讨论后写、不放弃部署。这些原则适用于任何 AI 协作场景。
